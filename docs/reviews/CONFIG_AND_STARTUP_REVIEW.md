## 1. P2：首次保存显示名时，将临时关闭问答的环境变量固化到本地配置

位置：`src/wxhook_api/core/chatbot_config.py:34`、`:63`。网页入口：`src/wxhook_api/routes/manage.py:108`。

`WXHOOK_CHATBOT_ENABLED=false` 用于临时关闭全部问答。加载时，`ChatbotOptions.enabled` 已经包含这个环境覆盖值；但第一次保存机器人显示名、目标本地文件尚不存在时，`save_mention_names()` 使用该运行时值初始化本地文件的 `enabled` 字段。

已沿真实网页配置接口隔离复现：

1. 临时目录的 `chatbot.yml` 配置为 `enabled: true`，没有 `chatbot.local.yml`。
2. 设置 `WXHOOK_CHATBOT_ENABLED=false`，加载得到暂停的机器人，符合临时关闭预期。
3. 调用 `/api/manage/chatbot/mentions` 仅修改显示名，接口报告保存成功。
4. 新建的 `chatbot.local.yml` 同时写入 `enabled: false`。
5. 移除环境变量后重新加载，仍然关闭问答；原 `chatbot.yml` 保持开启，但被新建的本地配置覆盖。

对照：目标本地文件已经存在且配置为开启时，保存显示名会保留其原始 `enabled: true`；移除临时环境变量后正常恢复。问题限于首次创建目标文件的分支，不是所有显示名保存都会改变开关。整个复现没有调用真实 Hook。

影响：原本只想临时关闭问答并修改机器人显示名，恢复环境后问答却持续关闭，仍需修改本地配置才能恢复。已有“环境变量优先”和“显示名保存立即生效”分别正常，问题是保存无关字段时混入运行时覆盖值。

建议：首次创建本地配置时，从原始有效文件或独立的持久化配置状态继承问答开关；显示名更新只改变显示名，不将环境变量覆盖结果写成长期设置。回归需要覆盖本地文件存在/不存在、临时关闭及移除覆盖后的重新加载。

## 2. P2：IPv6 监听配置的默认回调白名单与启动器生成地址不一致

位置：`src/wxhook_api/core/config.py:84`；`src/wxhook_api/launcher.py:113`、`:117`。

`service_url()` 已处理 IPv6 地址：监听 `::1` 或 `::` 时，启动器使用 `http://[::1]:8000` 访问本服务并生成回调地址。但未显式配置 `WXHOOK_ALLOWED_CALLBACK_URLS` 时，默认白名单只有 `127.0.0.1` 和 `localhost` 两种地址，没有 IPv6 回环地址。

隔离验证：

- 分别设置 `WXHOOK_HOST=::1` 和 `WXHOOK_HOST=::`，清除回调白名单环境覆盖。
- 配置加载成功，生成 `http://[::1]:8000/receiveChatBotMsg`，但该地址不在默认白名单。
- 实际 `manage_wechat()` 在创建 HTTP 客户端之前直接返回，启动状态为 `error`，提示自动回调地址不在白名单中；没有启动微信或执行回调配置。
- IPv4 对照 `127.0.0.1`、`0.0.0.0` 生成的回调地址均在默认白名单中。

影响：仅将监听地址改为本机 IPv6，默认一键启动流程便无法自动配置消息接收。服务本身可以继续运行；显式加入对应回调地址可以避开这个配置不一致。本轮没有绑定真实 IPv6 监听端口，也没有验证 DLL 对 IPv6 回调的实际兼容性。

建议：统一监听地址、启动器内部访问地址和默认回调白名单的生成规则，覆盖 IPv4 与 IPv6 回环；用户提供的显式白名单继续按原配置执行，不应自动扩大为任意地址。

## 3. P3：重启复用近期有效备份后，管理页仍显示“等待首次完成”

位置：`src/wxhook_api/services/backups.py:41`、`:164`；`src/wxhook_api/web/manage.js:992`。

新建 `BackupService` 时，`last_success_at`、`last_file` 初始化为空。调度器重启后会发现近期备份并延后下一次生成，但没有将已发现备份的信息恢复到诊断状态。

隔离复现：生成一份实际 ZIP 并验证其完整性，随后针对同一数据库和备份目录创建新的服务实例。运行一轮调度后：

- 正确识别并复用该文件，没有再次生成备份，下一次等待时间接近默认的 24 小时。
- 备份文件仍在，ZIP 检查通过，状态中没有生成或清理错误。
- `last_success_at`、`last_file` 仍为空。
- 管理页的现有分支在这个状态下显示“自动备份等待首次完成。”，直到本进程成功生成下一份备份才更新。

这是恢复后诊断与已有文件不一致，没有发现备份丢失或恢复数据损坏。普通重启后可能持续接近完整备份周期，容易让管理员误判自动备份尚未工作。

建议：启动时区分“本进程生成结果”和“已发现的最近备份”，校验已有文件后恢复对应诊断，或明确展示最近文件与校验状态。不能仅凭符合命名规则就宣称 ZIP 有效，也无需为了更新显示而额外生成和轮换备份。
