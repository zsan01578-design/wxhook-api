## 实施结果（2026-10-23）

已按本报告完成首批稳定性改造：

- 群/成员策略写入与权限快照读取位于同一事务，成功提交后才发布内存状态；读取或提交失败一起回滚。
- 回调消费者退出后拒绝接收新消息，新增 `/ready` 检查已启用后台任务，并在管理页展示后台完成/失败、队列和脱敏异常。
- 增加持久化收件表，在落盘后确认回调。归档阶段最多尝试三次，未进入自动处理的收件记录支持重启恢复；进入自动处理前保存不重放标记。没有有效消息 ID 时，同一收件记录仍能幂等归档。账号不匹配不重试，已经进入自动处理阶段的记录不会因恢复而重复发送。
- 媒体新增低磁盘空间保护，默认预留 1024 MiB；存储盘不可用也会报告失败，避免无效路径导致检查循环。

## 已复现：优先修复

### 1. P1：策略提交成功、缓存刷新失败时，自动处理继续使用旧权限

位置：`src/wxhook_api/services/groups.py:159`，`_write_policy()`。

当前先执行并提交 `action`，再另开连接执行 `_reload()`。如果第二步发生临时数据库读取故障，管理操作会报告失败，但数据库中的黑名单已经生效，`allowed()` 使用的内存缓存仍允许该群或成员继续处理。正常消息归档不会刷新这个缓存，直到另一次策略写入成功或服务重新启动才恢复一致。

使用临时数据库分别验证了群黑名单和成员黑名单：数据库 `blocked=1`，同时 `allowed(group, member)=True`；继续接收消息也不能修复缓存。

建议：运行中的策略修改在同一事务内读取待发布的策略快照，读取失败则回滚；提交成功后再发布内存状态。若仍保留分开的提交和重载，必须在状态不确定时暂停自动处理，并提供有界重试及明确的恢复状态。保留现有取消等待和写入锁保护。

验收：覆盖群/成员拉黑、关闭群功能、解除限制，分别注入快照读取失败、事务提交失败和重复取消，检查数据库、缓存及出站权限始终一致。

### 2. P1：回调消费者退出后，入口仍确认接收，健康检查仍正常

位置：`src/wxhook_api/services/events.py:74`、`src/wxhook_api/routes/health.py:12`。

`enqueue()` 只检查 `_accepting`，没有核对 supervisor 是否已退出。消费者取消信号传播后，supervisor 会收尾其余消费者，但不会清除 `_accepting`。已验证：工作任务结束后，回调仍返回 HTTP 200，消息留在内存队列无人消费；`/health` 仍返回 `status=ok`。

这里通过受控取消验证失效模式，不代表普通业务异常都会导致消费者退出；普通 `Exception` 已有捕获。

建议：消费者整体退出时关闭接收，入口核对任务存活并返回 503；保留 `/health` 的存活检查用途，另设业务就绪检查，暴露消费者数量、队列深度、处理中数量、处理失败次数和最近成功时间。队列存在积压时才判断是否长期无进展，避免空闲误报。自动恢复需要先完成旧任务收尾，不能盲目重放已经尝试的微信发送。

验收：取消、异常退出、停机、重新启动、队列满载，以及无消息时的正常空闲；消费者不可用时不能确认接收新消息。

### 3. P1：回调已经确认，临时归档失败后没有本地恢复记录

位置：`src/wxhook_api/routes/callbacks.py:37`、`src/wxhook_api/services/events.py:101`，应用首个关键处理器见 `src/wxhook_api/main.py`。

HTTP 200 表示成功进入内存队列。关键归档处理器发生数据库或账号核验异常时，消费者记录一条错误并跳过后续处理，随后将该条消息移出队列；没有本地持久化重试记录。回调诊断只记录入口 accepted/rejected，不记录这类后台处理失败。

隔离测试注入一次数据库异常：第一条回调 HTTP 200，归档数量为 0，accepted=1、rejected=0；下一条消息恢复正常，但第一条未被本地重试。历史同步在本机历史仍可读取时可能补回聊天记录，但历史导入不会补执行自动回复、关键词处理或媒体解析。同步关闭时没有这条历史补偿路径。

建议分两步：先增加处理成功/失败计数与脱敏故障状态，区分“已入队”和“已归档”；再设计持久化收件记录，在安全落盘后确认接收，采用有上限和退避的恢复策略。账号变化等保护性拒绝应保持暂停，不能作为普通瞬时故障反复执行；已经尝试的微信发送继续沿用现有去重和“结果未确认不自动补发”规则。

验收：数据库短暂不可写、Hook 短暂断开、落盘后进程退出、同消息重复回调、恢复中账号变化及发送确认丢失。先明确哪些步骤可以重试，再实现恢复，避免补偿造成重复发送。
