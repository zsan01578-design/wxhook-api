## 1. P2：备份轮换先删除旧副本，再检查最新副本，可能只留下损坏文件

位置：[backups.py:145](D:/wxhook/src/wxhook_api/services/backups.py:145)、[backups.py:195](D:/wxhook/src/wxhook_api/services/backups.py:195)。

`_prune()` 按文件名及文件安全属性选出最新 N 份，没有验证 ZIP 是否可用。后台循环先执行 `cleanup()`，之后才通过 `_discover()` 验证最新副本。发现损坏后仅写入诊断，下一次备份仍按这个损坏文件的修改时间计算。

隔离复现步骤：

1. 用实际 `run_once()` 生成两份有效备份，原保留数量为 2。
2. 仅损坏临时目录中的最新 ZIP，模拟存储损坏。
3. 重启备份服务并将保留数量设为 1，执行真实后台循环的首轮清理和发现逻辑。
4. 旧的健康备份被删除，只留下损坏 ZIP；诊断提示完整性失败，但未调用新快照生成，下一次尝试仍要等待约 **86400 秒**。

对照：两份备份都健康时，相同保留数量调整正常保留最新文件，恢复诊断也正常。

影响限于满足上述条件的备份集合，不表示原管理数据库被删除。风险在于轮换会进一步削弱已经发生损坏时的恢复能力。文件名符合规则不应等同于可恢复副本。

建议：先验证将保留的副本，再决定删除哪些旧副本；损坏文件不计入有效保留数量，至少保护最后一份已验证副本。发现最新副本不可用时，应按失败恢复策略安排重新生成，而不是用损坏文件的时间推迟整个周期。

## 2. P2：对话模型与搜索响应仍缺少受限解压和压缩流完整性检查

位置：[chat_model.py:290](D:/wxhook/src/wxhook_api/services/chat_model.py:290)、[web_search.py:133](D:/wxhook/src/wxhook_api/services/web_search.py:133)。同类读取还出现在 [chat_model.py:97](D:/wxhook/src/wxhook_api/services/chat_model.py:97) 的 HTTP 400 错误体处理中，本轮没有单独对该错误分支执行探针。

这两条成功响应路径直接使用 `response.aiter_bytes()`，HTTPX 完成解压后，应用才检查 256 KiB 的累计大小。之前媒体、解析页面和生图路径使用的 `core/bounded_http.py` 尚未覆盖这里。

已复现两个独立边界：

- **解压内存上限滞后**：模拟线上流式响应仅传输 **4098 字节** gzip 数据，HTTPX 解码器一次返回 **4194304 字节（4 MiB）**。两条路径最终都会报内容过大并关闭响应，但分配已发生，256 KiB 限制未约束解码过程。
- **缺少压缩完整性校验**：把合法模型 JSON / 搜索 JSON 压缩后删除末尾 8 字节 gzip 校验尾部，两条实际 provider 调用仍返回成功结果。完整 gzip 对照同样成功。该探针证明缺少 EOF/校验尾部不会被拒绝，不代表任何截断 JSON 都会被接受，也不证明返回的文本已经被篡改。

本轮只使用 4 MiB 小型模拟数据，未做内存耗尽测试，也未观察到进程崩溃。实际风险来自异常或高压缩率上游响应，可能造成超过预期的瞬时内存与解压开销；未完成的压缩传输也可能被报告为成功。

建议：让模型、搜索和用于判断备用模型切换的错误响应体共用现有受限读取器，分别限制传输量、解压累计量、单次解压产出，并检查压缩流结束状态。保留各路径自身的内容大小上限和脱敏错误行为；增加完整/截断 gzip、普通超限与压缩超限对照测试。
